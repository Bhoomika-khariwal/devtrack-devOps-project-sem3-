1. Introduction to CI/CD

CI/CD is a set of practices that helps teams integrate, test and deliver software changes frequently and reliably. CI stands for Continuous Integration. CD can mean Continuous Delivery or Continuous Deployment.

Code→ Build→ Test→ Release→ Deploy

Why do teams use CI/CD?

  • Detect code problems earlier.
  • Reduce repetitive manual tasks.
  • Make testing consistent.
  • Provide faster feedback to developers.
  • Support frequent, reliable software releases.
Example: When a student pushes a change to GitHub, an automated workflow checks the code and runs tests before the team considers deploying it.

2. CI vs Continuous Delivery vs Continuous Deployment

Continuous Integration

Integrate code frequently and automatically build and test it.

Continuous Delivery

Keep tested software ready to release, often with manual production approval.

Continuous Deployment

Automatically deploy changes that pass all required checks.

PracticeMain Purpose
CIBuild and test integrated code.
Continuous DeliveryPrepare changes for reliable release.
Continuous DeploymentAutomatically release approved changes after required checks.
Is Continuous Delivery the same as Deployment?

No. Continuous Delivery makes a release ready, while Continuous Deployment automatically releases changes after the pipeline's required checks pass.

3. CI/CD Pipeline Architecture

A pipeline is an automated sequence of stages. Each stage performs a particular task and reports success or failure.

Git Push→ Checkout→ Build→ Test→ Deploy
Checkout

Retrieve the repository's code for the workflow to use.

Build

Install dependencies, compile code or prepare an application artifact.

Test

Run automated checks to verify expected behavior.

Deploy

Release the validated application to a target environment when permitted.

A failed required test should normally prevent the dependent deployment job from running.

4. Introduction to GitHub Actions

GitHub Actions is GitHub's workflow automation platform. It can run tests, builds, security checks and deployments in response to repository events.

Important Terms

TermMeaning
WorkflowAutomation defined in a YAML file.
EventAn activity that can trigger a workflow.
JobA collection of steps running on a runner.
StepAn individual action or shell command.
RunnerThe machine executing the job.
ActionA reusable automation component.
GitHub Event→ Workflow→ Job→ Steps

5. Understanding YAML Workflow Files

GitHub Actions workflow files are stored in .github/workflows/ and use .yml or .yaml.

Example: Python CI Workflow

name: Python CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install pytest

      - name: Run tests
        run: python -m pytest

This is an example workflow for a Python project that has a requirements.txt file and pytest-compatible tests. Adjust the dependencies and commands for your own repository.

Why is YAML indentation important?

YAML uses indentation to represent structure. Incorrect indentation can make a workflow invalid or change how its settings are interpreted.

What does uses mean?

The uses keyword runs a reusable action, while run executes a shell command.

6. Workflow Triggers and Runners

A workflow can start automatically when an event occurs or manually when configured to allow it.

push

Starts on matching repository push events.

pull_request

Runs on configured pull request events.

workflow_dispatch

Enables manual workflow execution.

schedule

Runs workflows on a configured schedule.

Manual Trigger Example

on:
  workflow_dispatch:

Runner Example

jobs:
  example:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Hello from DevTrack"
GitHub-hosted runners provide managed execution environments. Self-hosted runners are maintained by the organization or developer.

7. GitHub Secrets and Pipeline Security

Applications sometimes need credentials to access external services. These should not be hardcoded into source code or workflow files.

Repository Secrets

In GitHub, repository administrators can configure secrets under repository Settings → Secrets and variables → Actions.

Example Secret Reference

env:
  API_TOKEN: {% raw %}${{ secrets.API_TOKEN }}{% endraw %}

Good Security Practices

  • Never commit passwords or API tokens.
  • Give workflows only the permissions they need.
  • Protect deployment environments.
  • Review third-party actions before using them.
  • Do not print secret values into logs.
This page only explains how secret references work. Never paste real credentials into a learning simulator.

8. Automated Testing and Pipeline Failures

Automated tests help teams detect errors before deployment. A pipeline may run unit tests, integration tests and other checks.

Example Test Command

python -m pytest

When a Test Fails

Build Passes→ Test Fails→ Inspect Logs→ Fix and Retry

Developers should read the failed step's logs, identify the cause, correct the code or test configuration and rerun the workflow.

What if the build succeeds but tests fail?

The workflow is not successful overall. Deployment jobs that depend on the successful test job should not run.

9. Continuous Delivery and Deployment

Deployment moves an application version into a target environment. Teams often use separate development, staging and production environments.

Build→ Test→ Staging→ Approval→ Production

Common Deployment Strategies

  • Rolling: Update instances gradually.
  • Blue-Green: Switch traffic between two environments.
  • Canary: Release to a small group first.
  • Rollback: Return to a previously working version.
Real deployment requires a configured target environment and appropriate authorization. The simulator below does not deploy real software.

10. Monitoring and Continuous Feedback

After deployment, teams monitor software to detect problems and improve reliability.

Logs

Records of application and system events.

Metrics

Measurements such as latency and error rate.

Alerts

Notifications when monitored conditions need attention.

Feedback

Information used to improve future releases.

Deploy→ Monitor→ Feedback→ Improve
