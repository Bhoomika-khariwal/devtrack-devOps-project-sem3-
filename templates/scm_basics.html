1. Introduction to SCM

Software Configuration Management (SCM) is the systematic process of identifying, tracking, controlling and recording changes to software throughout its lifecycle.

SCM is broader than Source Code Management. Source Code Management mainly tracks code changes, while Software Configuration Management also covers requirements, documentation, configurations, releases and other project artifacts.

Identify→ Track→ Control→ Verify

Example

A college team develops an attendance website. One member changes the login page, another updates the database, and another edits documentation. SCM helps track which files changed, who changed them, why they changed and which versions belong to a release.
SCM vs Source Code Management

Source Code Management is focused on versioning code. Software Configuration Management covers the wider process of managing controlled software artifacts and changes. Git is a source version control tool that supports SCM activities.

2. Need and Objectives of SCM

When several developers work on one project, files may change simultaneously. Without proper management, teams may overwrite changes, lose working versions or release inconsistent software.

Traceability

Record what changed, when and why.

Consistency

Keep project artifacts aligned.

Collaboration

Support multiple contributors safely.

Recovery

Retrieve previous working versions.

Main Objectives

  • Identify important software artifacts.
  • Maintain controlled versions of those artifacts.
  • Review and approve changes when required.
  • Record the status and history of changes.
  • Verify that releases contain correct items.
  • Support reproducible software builds.
What happens without SCM?

A developer might overwrite another person's work, an untested file might enter a release, or the team might not know which version was deployed. SCM reduces these risks through versioning, review and configuration control.

3. Software Configuration Items

A Software Configuration Item (SCI) is an identifiable software-related artifact that is placed under configuration control.

Examples of SCIs

Source Code

Python, JavaScript and HTML files.

Documentation

Requirements, design documents and manuals.

Test Artifacts

Test cases, scripts and reports.

Configuration Files

Application settings and deployment definitions.

Configuration Item Attributes

  • Unique identification or name.
  • Version or revision.
  • Owner or responsible team.
  • Current status.
  • Relationships with other items.
In DevTrack, app.py, templates/scm_basics.html, static/style.css and test scripts can be treated as configuration items.

4. Software Configuration Management Process

SCM includes several connected activities. Their exact organization may differ between projects and companies.

Identification→ Change Control→ Status Accounting→ Audit
1. Configuration Identification

Select the items that need to be managed, assign identifiers and define their versions and relationships.

2. Configuration Change Control

Evaluate proposed changes, assess their impact, obtain approval where required and implement approved modifications.

3. Configuration Status Accounting

Record and report configuration information, such as item versions, approved changes, pending requests and release status.

4. Configuration Auditing

Check that configuration items and releases match their approved requirements, records and expected contents.

Why These Activities Matter

Together, they help teams know which version is correct, what modifications were approved and whether the delivered software matches the intended configuration.

5. Configuration Identification and Baselines

What is a Baseline?

A baseline is a formally established version of a configuration that serves as a reference for future work. Changes to a controlled baseline follow an agreed change-control process.

Initial Version→ Review→ Approved Baseline→ Controlled Changes

Example

A team approves version 1.0 of a college portal for release. That version becomes a reference baseline. Later changes can be compared against it and included in future approved releases.

Baseline vs Git Commit

A Git commit records a snapshot in repository history. A baseline is an approved reference configuration. A team may use a Git tag or specific commit to identify a baseline, but not every commit is automatically a baseline.

What is a release tag?

A Git tag is a named reference to a commit. Teams commonly use tags such as v1.0.0 to identify release versions. Approval and release controls are defined by the team's process.

6. Introduction to Version Control

Version Control is a method of recording changes to files over time so that teams can inspect, compare and recover versions.

Why Use Version Control?

  • Maintain a history of changes.
  • Identify contributors to changes.
  • Compare older and newer file versions.
  • Support parallel development.
  • Recover earlier versions when needed.

Important Terms

TermMeaning
Repository Stores tracked files and version history.
Working Directory Files currently being edited.
Staging Area Changes selected for the next commit.
Commit A recorded snapshot in Git history.
Branch An independent line of development.
Remote A repository stored at another location.
Edit Files→ Stage→ Commit→ Push

Basic Git Commands

git status
git add index.html
git commit -m "Update homepage"
git log --oneline

These commands check repository status, stage a file, create a commit and display a compact commit history.

7. Types of Version Control Systems

Local VCS

Maintains file revision information on one computer.

Centralized VCS

Uses a central repository server. Example: SVN.

Distributed VCS

Developers maintain local repositories with project history. Examples: Git and Mercurial.

Centralized vs Distributed VCS

Feature Centralized Distributed
Repository Central server Local copies plus optional remotes
Offline commits Usually require server access Supported locally
History Primarily centralized Stored in local clones
Examples SVN Git, Mercurial
Does distributed mean no central server?

No. Distributed systems such as Git can still use GitHub or GitLab as shared collaboration servers. The key difference is that developers also have local repository history.

8. Change Control and Configuration Management

Change Control is a process for evaluating and managing proposed modifications to controlled project items.

Request→ Review→ Approve→ Implement→ Verify

Example Change Request

A college requests an attendance export feature. The team records the requirement, checks its impact, approves the work, implements the feature, tests it and records the final version.

Change Control vs Version Control

Version Control records file revisions. Change Control decides how proposed changes are evaluated, authorized and verified. Both support SCM.

What is a Change Control Board?

A Change Control Board (CCB) is a group responsible for reviewing and deciding on certain change requests in projects that use formal approval procedures. Small projects may use simpler review processes instead.

Configuration Audits

  • Functional audit: verifies that required functions and behavior are satisfied.
  • Physical audit: verifies that the delivered configuration matches its documented contents.

9. Branching, Merging and Conflicts

What is Branching?

A branch lets developers work on features or fixes without immediately changing the main development line.

main→ feature branch→ review→ merge

Branch Commands

git switch -c feature-login
git status
git add .
git commit -m "Add login feature"
git switch main
git merge feature-login

This is an example workflow. In a shared repository, teams commonly review a feature through a pull request before merging it.

What is a Merge Conflict?

A merge conflict occurs when Git cannot automatically combine certain changes, such as incompatible edits to the same part of a file.

How do teams resolve conflicts?

Developers inspect the conflicting changes, decide the correct final content, edit the file, test the result and mark the conflict as resolved. Git then allows the merge to be completed.

Common Branching Models

  • Feature branching: each feature is developed in its own branch.
  • GitFlow: uses defined branches for features, releases and hotfixes.
  • Trunk-based development: developers integrate small changes frequently into a shared main line.

10. Git vs SVN vs Mercurial

Git, Subversion (SVN) and Mercurial are version control systems.

Feature Git SVN Mercurial
Model Distributed Centralized Distributed
Local commits Yes Normally no Yes
Branching Lightweight branches Directory-based branches Multiple branching methods
Example command git commit svn commit hg commit

Git vs GitHub

Git is a version control system. GitHub is a platform that hosts Git repositories and provides collaboration features such as pull requests, issues and GitHub Actions.

GitHub and GitLab are hosting and collaboration platforms. They are not separate replacements for the Git version control system.

11. Practical SCM Workflow

Let's understand a basic collaboration workflow using a college website project.

Step 1 — Create a Repository

git init
git status

Step 2 — Add Project Files

git add .
git commit -m "Initial project setup"

Step 3 — Create a Feature Branch

git switch -c feature-dashboard

Step 4 — Record Your Changes

git add .
git commit -m "Add dashboard feature"

Step 5 — Push to GitHub

After configuring the GitHub remote named origin, push your feature branch: 

git push -u origin feature-dashboard

Step 6 — Review and Merge

Create a pull request on GitHub. Review the changes, run required tests and merge the feature after approval.

Step 7 — Update Your Local Main Branch

git switch main
git pull origin main
These commands are learning examples, not instructions to run inside your current DevTrack repository. Practice them in a separate sample repository.

How SCM Supports DevTrack

Your DevTrack team can use separate feature branches for learning modules, quizzes and interface changes. Git commits record progress, while pull requests help review and integrate completed features.
